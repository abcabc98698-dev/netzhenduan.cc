# v2rayNG 分应用代理与精准分流配置指南：黑白名单模式选择、国内常用银行/国企办公 App 防阻断实战

在移动端使用科学上网客户端时，许多用户经常陷入两难困境：开启代理后，虽然能够顺畅浏览 YouTube、查阅文献与使用即时通讯软件，但打开手机银行、个人所得税、钉钉打卡或国企内部 OA 系统时，往往会遭遇“检测到高危代理环境拒绝登录”、“网络连接异常代码 5001”或支付滑块验证风控；而如果直接关闭代理，海外关键业务数据流又会瞬间中断。

这种矛盾的根本诱因在于：**传统的全局代理模式粗暴地将整台手机所有应用程序的数据包全量重定向至虚拟网卡，不仅破坏了国内应用对真实地理位置的信任，更导致大流量文件跨洋绕行带来高延迟与机房封控**。

在 Android 操作系统中，`VpnService` 提供了基于 Linux UID（User ID）沙盒隔离的精细化流量路由控制能力——**分应用代理（Per-App Proxy / Split Tunneling）**。掌握该特性的正确编排，是实现“海外学术/开发应用极速出海、国内金融/办公软件原生地面直连”的必修课。

## 模块一：核心问题与底层机制：Android VpnService 路由拦截原理

与桌面操作系统（Windows 的 WinINet 注册表或 TAP 网卡）不同，Android 是一套以 Linux 内核为底座、构建于应用沙盒机制之上的多用户操作系统。每一个独立安装的 App，系统都会为其分配一个独占的 Linux 用户标识符（UID，数值范围通常为 10000 至 19999）。

当 v2rayNG 在前台被用户激活时，它会向系统发起 `VpnService.Builder` 接口调用：

```
+─────────────────────────────────────────────────────────────────────────────+
|               Android 操作系统底层分应用代理数据包拦截时序流                |
+─────────────────────────────────────────────────────────────────────────────+
[用户空间应用层]
  App A (Telegram, UID 10185)         App B (招商银行, UID 10092)
        │ (发包: 源端口/目标端口)              │ (发包: 源端口/目标端口)
        ▼                                     ▼
[Linux 内核网络栈与策略路由决策]
  IP 报文生成 -> 读取 socket.sk_uid -> 匹配内核 fwmark (防火墙标记)
        │                                     │
  [命中代理白名单 UID 10185]            [未在代理白名单中 (UID 10092)]
        │ (打上 fwmark 标记 0x1001)           │ (不打标记，保持默认直连)
        ▼                                     ▼
  重定向至虚拟网卡 (tun0, 10.0.0.2)     交由物理出口网卡 (wlan0 / 5G 基带)
        │                                     │
        ▼                                     ▼
  v2rayNG Core (Xray tun2socks)        基站 / 家用路由器物理出口 (光速直连)
        │                                     │
        ▼ (加密封装跨越大洋)                   ▼ (毫秒级直达国内网银服务器)
  境外专线落地机 (香港/日本)           招商银行国内核心机房 (安全可信 IP)
```

### 1. 内核策略路由与网络命名空间绑定
当系统执行 `VpnService.Builder.establish()` 时：
- Android 网络管理服务（`netd`）会在内核中动态创建一张专用路由表（例如 `table 1002`）；
- 核心策略规则为：所有打上特定防火墙标记（`fwmark`）的数据包，其默认下一跳强制设定为虚拟设备 `tun0`；
- v2rayNG 通过调用 `addAllowedApplication(String packageName)` 或 `addDisallowedApplication(String packageName)`，向系统内核注册允许或禁止绑定的包名集合。系统底层的 `ConnectivityService` 会将包名解析为对应的数字 UID，并在 socket 创建时决定是否将其绑定至该专用路由表。

### 2. 避免套接字自我循环的物理保护
v2rayNG 自身进程（通常为 `com.v2ray.ang`，UID 如 10230）在将流量加密打包后，必须向境外服务器建立实际的物理 TCP/UDP 传输通道。
- 如果代理自身发出的流量也被卷入 `tun0`，系统将发生无限回环死锁；
- Android 机制要求代理客户端显式调用 `VpnService.protect(int socketFd)`。操作系统接收到该系统调用后，会绕过 VPN 策略路由规则，强制将该 Socket 绑定到系统的底层物理网络（WiFi 物理适配器 `wlan0` 或蜂窝数据适配器 `rmnet0`），保障真实出站流量物理畅通。

## 模块二：模式选择与策略对比矩阵：白名单 vs 黑名单

在 v2rayNG 的「分应用代理」设置中，提供了两种截然不同的策略逻辑。用户必须根据自己的设备定位做出明确选型：

```
+─────────────────────────────────────────────────────────────────────────────+
|               分应用代理两大模式的核心哲学与安全边界对比                    |
+─────────────────────────────────────────────────────────────────────────────+
[模式一：白名单模式 (仅允许选中的应用通过代理)]
  核心哲学: 最小特权原则 (Default DENY / Explicit ALLOW)
  行为边界: 默认全直连，只有明确打勾的应用才会走代理隧道
  防护等级: ★★★★★ (绝对防御国内银行、国税、OA 误伤)

-------------------------------------------------------------------------------

[模式二：黑名单模式 (仅排除选中的应用)]
  核心哲学: 全量接管原则 (Default ALLOW / Explicit DENY)
  行为边界: 默认全代理，只有打勾的应用才会排除走直连
  防护等级: ★★☆☆☆ (新安装应用极易意外漏网走代理，导致风控)
+─────────────────────────────────────────────────────────────────────────────+
```

### 八维度工程特性横向对比表

| 评估维度 | 白名单模式 (仅允许所选应用) | 黑名单模式 (仅排除所选应用) |
|---|---|---|
| **核心安全策略** | **默认直连（零误伤原则）** | 默认代理（全量接管原则） |
| **手机银行风控风险** | **零风险（网银完全感知不到 VPN）** | 高风险（漏选一个银行即触发拦截） |
| **新装 App 影响** | 默认直接走国内网络，安全稳定 | 默认走境外代理，极易意外走漏敏感流量 |
| **系统组件与推送影响**| 系统底层完全不受代理干扰，推送稳定 | 极易意外接管系统更新与应用市场 |
| **日常配置维护量** | 极低（只需勾选 5~10 个特定出海 App） | 较高（需持续将国内软件纳入排除列表） |
| **设备电池与 CPU 开销**| **极轻（仅处理被勾选 App 的报文）** | 较重（整机所有后台心跳全部经由内核解包） |
| **双开/分身应用兼容性**| 优秀（对沙盒隔离要求明确） | 一般（分身 UID 容易逃逸排除列表） |
| **推荐适用场景** | **绝大多数国内日常主力机、办公手机** | 极客测试机、原生海外系统（Pixel 原生） |

> [!IMPORTANT] 生产级核心建议
> 在国内主力 Android 手机上，**强烈建议选择「白名单模式」**！
> 在白名单模式下，您只需勾选 Chrome、Telegram、Twitter、YouTube 等少数海外应用。包括微信、支付宝、银行客户端在内的数百个国内系统软件将彻底运行于系统原生直连通道中，不仅杜绝了风控误伤，更能大幅降低手机发热与耗电。

## 模块五：金融/政企应用防风控专章：底层反欺诈对抗机理

国内金融机构与政企平台的安全加固组件（如梆梆安全、爱加密、通付盾等安全 SDK）在 App 启动与转账鉴权时，会执行多维度环境纯净度检测：

```
+─────────────────────────────────────────────────────────────────────────────+
|               网银客户端安全 SDK 探测网络环境微观流程图                     |
+─────────────────────────────────────────────────────────────────────────────+
网银 App 启动
  │
  ├─► [探测 1: 系统网卡枚举] 遍历 NetworkInterface.getByName("tun0")
  │     ├── [全局模式/黑名单漏排] ──► 发现活动 tun0 网卡 ──► 标记高危代理环境 (拒绝登录)
  │     └── [白名单模式未勾选] ──► 沙盒被隔离，无法感知 tun0 ──► 通过检测
  │
  ├─► [探测 2: 出口公网 IP 与 ASN 纯净度审计] 发起 HTTPS 请求获取客户端出口 IP
  │     ├── [流量误走境外代理] ──► 出口 IP 为境外机房 ASN (Hosting) ──► 触发反欺诈拦截
  │     └── [流量物理网卡直连] ──► 出口 IP 为本地家庭宽带/5G 基站 (ISP) ──► 安全放行
  │
  └─► [探测 3: 域名解析一致性] 校验核心业务域名是否被解析至保留 IP (198.18.x.x)
        ├── [被 Fake-IP 接管] ──► 判定遭遇 DNS 劫持/中间人攻击 ──► 阻断交易
        └── [真实运营商 Local DNS] ──► 解析返回国内 CDN 节点 ──► 交易成功
```

### 为什么只有「白名单模式」能 100% 免疫网银拦截？
在全局代理或配置不当的黑名单模式下，即便通过路由规则将网银域名设为 `direct`（直连），网银进程依然运行于 VPN 建立的全局虚拟网络命名空间内。安全 SDK 仅需调用 Java 的 `NetworkInterface.getNetworkInterfaces()`，发现系统中存在 `tun0` 接口且 MTU 异常，就会直接触发反欺诈策略。
而在**白名单模式**下，操作系统在系统服务层直接将网银 UID 排除在 VPN 空间之外。网银 SDK 遍历系统网络接口时，**只能看到 `wlan0` 或 `rmnet0`，物理上完全探测不到 `tun0` 的存在**，从而彻底根除被风控误伤的物理根源。

## 模块六：多用户与分身空间避坑：微信双开/隐私空间 UID 穿透

国产定制系统（小米 HyperOS、vivo OriginOS、OPPO ColorOS、荣耀 MagicOS）普遍支持「应用双开（应用分身）」或「隐私系统空间」。这一功能在 Android 底层依托的是 **多用户框架（Multi-User Framework）**：

### 1. 多用户 UID 编码算法
Android 底层的 UID 计算公式为：
$$\text{Linux UID} = \text{User ID} \times 100000 + \text{App ID}$$
- **主空间（User 0）**：微信主程序 UID = $0 \times 100000 + 10088 = 10088$；
- **分身空间（通常为 User 999）**：微信分身 UID = $999 \times 100000 + 10088 = 99910088$。

### 2. 双开应用分流失效的诱因与自救
部分旧版本 v2rayNG 在读取系统已安装应用列表时，仅调用了 `pm.getInstalledPackages(0)`，只能读取 User 0（主用户空间）的软件列表。
- **灾难后果**：如果用户配置了白名单模式，但列表中无法勾选分身空间的海外应用（如 Telegram 分身），该分身应用将因为没有主空间匹配项而被系统默认走直连，导致无法出海；
- **排错方案**：
  1. 确保 v2rayNG 升级至最新稳定版（新版已原生适配多用户空间枚举）；
  2. 若分身应用依然断网，可在 v2rayNG 设置中切换为「自定义路由规则」，依托底层 Xray 内核的 `geosite` 与 `geoip` 分流，不依赖应用层的 UID 过滤。

## 模块七：Google 基础框架调度策略：GMS 与 Play 商店精细化放行

许多用户在使用海外应用时，依赖 Google 基础服务框架（Google Mobile Services，GMS）推送即时通知或进行应用内购买。如果只勾选了目标 App 而遗漏了 GMS，将导致应用频繁弹窗“Google Play 服务停止运行”或无法登录 Google 账号。

### Google 套件最小化放行清单
在「分应用代理」中开启“显示系统应用”后，必须确保以下三大核心组件被纳入代理白名单：

```
+─────────────────────────────────────────────────────────────────────────────+
|               Google 移动服务套件 (GMS) 核心组件依赖拓扑                    |
+─────────────────────────────────────────────────────────────────────────────+
目标出海应用 (如 Twitter / YouTube)
  │ (依赖账号验证与 FCM 消息推送)
  ▼
[核心 1: Google Play 商店] ──► 包名: com.android.vending (负责授权校验与更新)
  │
  ▼
[核心 2: Google Play 服务] ──► 包名: com.google.android.gms (底层通信总线)
  │
  ▼
[核心 3: Google 服务框架]   ──► 包名: com.google.android.gsf (账号同步与安全证书)
```

> [!TIP] 电池优化建议
> 将 `com.google.android.gms` 纳入代理白名单后，手机能够通过原生的 FCM（Firebase Cloud Messaging）长连接在后台低功耗接收海外推送消息，无需各海外 App 在后台常驻拉活，整机待机续航可提升 15% 以上。

## 模块九：自动化脚本与 ADB 诊断工具：深入排查 VpnService 状态

当手机分应用代理出现不可预知的路由异常时，可通过 USB 连接电脑并在 ADB 终端中运行以下脚本，精准提取 Android `ConnectivityService` 与 `VpnService` 的底层运行快照：

```bash
#!/bin/sh
# ==============================================================================
# netzhenduan.cc Android VpnService 策略路由与分应用代理深度审计脚本
# ==============================================================================

echo "=========================================================="
echo "    Android 系统底层 VpnService 与分应用代理状态审计"
echo "=========================================================="

# 1. 检查当前 VPN 运行包名与所有者
echo "\n[1/4] 检索当前接管系统的 VPN 应用程序..."
VPN_DUMP=$(dumpsys vpn 2>/dev/null)
CURRENT_PKG=$(echo "$VPN_DUMP" | grep "mPackage:" | awk '{print $2}')
if [ -n "$CURRENT_PKG" ]; then
    echo "  [OK] 活动 VPN 归属包名: $CURRENT_PKG"
else
    echo "  [FAIL] 系统当前未运行任何 VpnService！"
    exit 1
fi

# 2. 检查 VpnService 的分应用代理模式与 UID 列表
echo "\n[2/4] 解析 VpnService 白名单/黑名单 UID 过滤表..."
echo "$VPN_DUMP" | grep -E "mAllowedApplications|mDisallowedApplications" | while read -r line; do
    echo "  [CONFIG] $line"
done

# 3. 审计策略路由与网卡接口
echo "\n[3/4] 检查系统网络接口与 MTU 设定..."
ip addr show tun0 2>/dev/null | grep -E "mtu|inet " | while read -r line; do
    echo "  [INTERFACE] $line"
done

# 4. 测试特定应用的 UID 策略归属
echo "\n[4/4] 检查国内关键应用是否成功避开 VPN 空间..."
CHECK_APPS="com.tencent.mm cmb.pb com.eg.android.AlipayGphone"
for app in $CHECK_APPS; do
    APP_UID=$(pm list packages -U | grep "^package:$app " | awk '{print $2}' | cut -d':' -f2)
    if [ -n "$APP_UID" ]; then
        echo "  [APP] $app (UID: $APP_UID) -> 状态安全 (直连物理通道)"
    else
        echo "  [INFO] 未安装应用: $app"
    fi
done

echo "\n======================= 审计完成 ======================="
```

## 模块十：真实生产事故复盘：典型分流崩溃案例

### 案例一：国企员工因全局代理导致企业微信异地登录强制冻结
- **故障背景**：某大型国企软件工程师在手机上开启 v2rayNG 全局模式查阅海外技术文档。半小时后，其企业微信突然弹出安全警报强制退出，提示“账号在异地（美国洛杉矶）发起高危访问，已被管理员临时封禁”。
- **技术复盘与根因分析**：
  1. 企业微信内置了基于 IP 地理位置的自适应安全防护引擎；
  2. 用户在 v2rayNG 中未配置分应用代理，导致企业微信后台长连接心跳包全程走境外代理节点发送；
  3. 企业安全策略检测到员工账号在 5 分钟内地理位置从北京突变至洛杉矶，触发不可逆的跨国登录封锁机制；
- **根治措施**：彻底停用全局模式，开启 v2rayNG 分应用代理白名单模式，仅将浏览器与海外开发工具打勾，企业微信彻底走原生移动网络直连。

### 案例二：微信分身在白名单模式下无法收取任何消息
- **故障背景**：用户在小米手机上使用「应用双开」创建了微信分身。配置 v2rayNG 白名单模式并勾选了工作相关的海外应用后，微信分身偶发性断网，无法即时接收好友消息。
- **技术复盘与根因分析**：
  1. 用户此前曾将 v2rayNG 配置为黑名单模式，但在黑名单中仅排除了主空间的微信（UID `10088`），未排除分身空间的微信（UID `99910088`）；
  2. 随后切换至白名单模式时，配置文件缓存未彻底重置，底层内核的策略路由表中残留了部分分身空间的流量标记；
  3. 导致分身微信的部分长连接请求误入 `tun0`，但代理核心内部因规则不匹配将其丢弃；
- **根治措施**：在系统应用管理中清空 v2rayNG 的所有应用数据，重新配置白名单模式并重启手机，确保内核多用户路由表彻底刷新。

## 模块十一：分应用代理高频疑难排查矩阵

| 异常现象 | 物理底层诱因剖析 | 快速定位排查方法 | 工业级终极自愈方案 |
|---|---|---|---|
| **勾选的应用打不开，未勾选的应用也断网** | 系统私密 DNS（DoT）与 `VpnService` 冲突导致域名解析死锁 | 检查手机「设置 -> 私密 DNS」，查看是否显示连接失败 | 将手机系统私密 DNS 强制设置为「关闭」，由代理内部接管解析 |
