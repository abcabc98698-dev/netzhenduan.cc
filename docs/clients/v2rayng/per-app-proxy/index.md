## 模块一：Android 分应用代理底层 Linux UID 沙盒隔离架构

在 Android 操作系统中，每一个安装的应用程序都会被系统分配一个独一无二的 Linux 用户 ID（UID，如 `u0_a185`，对应数值如 10185）。Android 底层的进程沙盒正是通过 UID 实现权限与文件系统隔离的。
`VpnService` 引擎在创建虚拟网络适配器时，通过底层 Linux 内核的 `iptables` / `ebpf` 标记与策略路由（Policy Routing），直接在内核层依据 UID 对数据包实施拦截或放行：

```
+─────────────────────────────────────────────────────────────────────────────+
|               Android VpnService 分应用代理双模式底层拦截机理                |
+─────────────────────────────────────────────────────────────────────────────+
应用发包层:
┌───────────────────────────────┐     ┌───────────────────────────────┐
│ 海外受限应用: Telegram / X   │     │ 国内敏感应用: 微信 / 手机银行 │
│ (包名: org.telegram.messenger)│     │ (包名: com.tencent.mm)        │
│ UID: 10245 (沙盒空间 A)       │     │ UID: 10088 (沙盒空间 B)       │
└───────────────┬───────────────┘     └───────────────┬───────────────┘
                │ (原始 Socket 报文)                   │ (原始 Socket 报文)
                ▼                                     ▼
┌─────────────────────────────────────────────────────────────────────────────┐
│ Android 系统内核策略路由决策引擎 (VpnService Kernel Policy Routing)         │
│                                                                             │
│ [模式 A：白名单模式 (addAllowedApplication)]                                │
│   - 仅被勾选的应用 UID 报文被强制打上 fwmark 标记并重定向至 tun0 虚拟网卡    │
│   - 未勾选应用的数据包完全不经过 VPN 隧道，直接通过物理网卡 (wlan0) 直连基站│
│                                                                             │
│ [模式 B：黑名单模式 (addDisallowedApplication)]                             │
│   - 默认将整机所有应用数据包全部重定向至 tun0 虚拟网卡                      │
│   - 仅对被勾选的排除应用解除拦截，由物理网卡发出                            │
└───────────────────────┬─────────────────────────────┬───────────────────────┘
                        │ (命中代理应用报文)           │ (直连应用报文)
                        ▼                             ▼
         ┌─────────────────────────────┐       ┌─────────────────────────────┐
         │ tun0 网卡 ──► v2rayNG 内核  │       │ 物理网卡 (wlan0 / 5G 基带)  │
         │ (经过 Xray-core 规则与加密) │       │ (本地运营商光速直达国内机房)│
         └─────────────────────────────┘       └─────────────────────────────┘
```

### 1. `addAllowedApplication` (白名单代理模式)
- **底层行为**：向 `VpnService.Builder` 传入明确的应用程序包名列表。内核仅将这些指定 UID 的网络命名空间绑定至虚拟网卡 `tun0`；
- **核心优势**：**绝对安全与零性能损耗**。未勾选的微信、支付宝、银行软件在操作系统网络栈层面完全不知道 VPN 的存在，网银绝不会触发“检测到代理软件挂载”的误报，且直连网络零延迟损耗；
- **适用场景**：日常主力机、对金融隐私与国内办公稳定性要求极高的重度用户。

### 2. `addDisallowedApplication` (黑名单直连模式)
- **底层行为**：向 `VpnService.Builder` 传入排除的包名列表。内核将整机所有流量全部引导进入 `tun0`，仅放行被排除的应用直连物理网卡；
- **核心风险**：一旦新安装了未配置排除规则的国内应用（如新下载的政务 App），其流量会被默认送入代理隧道，极易触发异地登录风控；
- **适用场景**：备用机、海外常驻用户或海外版原生 Android 系统（Pixel 等）。

## 模块三：移动端分应用代理四大工程陷阱与避坑全景

在实际配置分应用代理时，许多用户即便勾选了应用，仍然会遭遇各种诡异故障。这源于 Android 系统深层的四大架构特性：

### 陷阱 1：UID 与组件拆分陷阱（以微信为例）
许多大型 Android 应用并非单进程单包名运行。例如微信不仅包含主包名 `com.tencent.mm`，其内置的 XWeb 内核、网页查看器可能在系统内部调用独立的 DownloadManager（系统下载管理器 `com.android.providers.downloads`）下载文件。如果开启了白名单代理模式而未放行下载管理器，点击外链下载将彻底卡死。

### 陷阱 2：国产定制系统「应用分身/应用双开」的 UID 偏移
在小米 HyperOS、vivo OriginOS 等系统中开启微信分身或支付宝双开时，系统会为分身应用分配一个虚拟多用户空间（User ID 通常为 999，如 UID 变为 `u999_a10088`）。部分旧版 v2rayNG 在分应用列表中仅列出了 User 0（主空间）的应用，导致双开的应用无法被白名单覆盖，瞬间回退至直连模式或出现路由混乱。

### 陷阱 3：私密 DNS 的套接字旁路劫持
如果手机开启了系统级私密 DNS（Private DNS），操作系统解析域名的请求是由系统核心进程 `system_server` 发起的，其 UID 为 `1000`（System UID）。在白名单代理模式下，由于 `system_server` 通常未被列入代理列表，其发往海外 DoT 服务器的解析报文直接走物理网卡直连，遭遇 GFW 丢包阻断，导致所有代理应用因解析失败而瘫痪。

### 陷阱 4：内网设备（IoT/智能家居）局域网直连阻断
当手机连接家庭 WiFi 并运行 v2rayNG 时，如果需要使用米家、群晖 NAS（DS finder）或投屏到电视，必须确保路由模式开启了「绕过局域网（Bypass LAN）」，否则发往 `192.168.x.x` 或 `10.x.x.x` 的局域网广播与 mDNS 组播报文将被强行吸入代理隧道，导致米家智能设备全线离线或搜不到投屏设备。

## 模块五：终端自动化：ADB 批量提取手机已安装应用包名脚本

当您在手机上安装了冷门办公软件或特定小众银行 App，无法确定其确切包名时，可通过 ADB 执行以下命令，秒级过滤出所有第三方应用包名：

```bash
#!/bin/sh
# ==============================================================================
# netzhenduan.cc Android 第三方应用包名批量检索与分类工具
# ==============================================================================

echo ">>> 正在列出手机中安装的所有第三方应用及对应 UID..."
pm list packages -3 -U | sort | while read -r line; do
    PKG_NAME=$(echo "$line" | cut -d':' -f2 | cut -d' ' -f1)
    UID_NUM=$(echo "$line" | grep -o 'uid:[0-9]*' | cut -d':' -f2)
    APP_LABEL=$(pm dump "$PKG_NAME" 2>/dev/null | grep -m1 "nonLocalizedLabel" | cut -d'=' -f2)
    echo "  [UID: $UID_NUM]  $PKG_NAME  (${APP_LABEL:-未知名称})"
done
```

## 模块六：真实生产环境分流故障根因分析（RCA）

### 案例一：招商银行 App 启动弹窗“检测到系统代理环境，拒绝登录”
- **故障现象**：某金融外企工程师在 Android 手机上开启 v2rayNG 访问企业邮箱，切换至招商银行 App 尝试转账时，App 瞬间弹出红色安全警报并强制退出，提示“检测到当前设备网络处于代理或可疑抓包环境”。
- **抓包与底层复盘**：工程师在 v2rayNG 中设置了“绕过局域网及大陆”，未开启分应用代理。招商银行客户端启动时，其反作弊 SDK（网银安全加固组件）调用了 `NetworkInterface.getNetworkInterfaces()` 遍历系统网卡，检测到存在名为 `tun0` 的活动虚拟网卡，且系统默认网关被修改为 `tun0`。即便该 App 的通信数据包实际走直连规则，SDK 依旧判定系统环境不纯净，触发硬性熔断；
- **自愈方案**：在 v2rayNG 设置中开启「分应用代理」，选择「仅允许选中的应用通过代理（白名单模式）」，**仅勾选海外应用，坚决不勾选任何手机银行 App**。在白名单模式下，Android 系统内核完全不将网银进程加入 VPN 虚拟网络空间，网银 SDK 无法探测到 `tun0` 的存在，警报解除，转账恢复。

### 案例二：微信朋友圈图片与高清原图转圈 30 秒超时
- **故障现象**：用户开启 v2rayNG 后，虽然能正常访问 YouTube 4K，但手机微信收取好友发来的高清原图时严重卡顿，需要等待 30 秒以上甚至提示加载失败。
- **抓包与底层复盘**：通过 Wireshark 配合 Android 抓包分析发现，微信获取图片的 CDN 域名为 `wx.qlogo.cn` 与各种腾讯 CDN IP。由于用户配置了黑名单模式但漏排了微信，且在 v2rayNG 中启用了“全局代理”，导致微信向腾讯图片 CDN 服务器发起的 HTTP 请求跨越大洋绕行至美国落地机。腾讯 CDN 识别到来自美国洛杉矶的出口 IP，将请求调度至北美腾讯边缘节点，跨洋大文件传输产生高达 180ms 延迟与晚高峰丢包，造成图片加载假死；
- **自愈方案**：将微信纳入分应用直连白名单，同时在 v2rayNG 路由设置中将预设规则切换为「绕过局域网及大陆地址（Bypass LAN and Mainland）」，使所有国内 CDN 报文直接由本地基站发出，微信图片加载重回毫秒级响应。
